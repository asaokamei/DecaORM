# fill メソッドのバッチ読み込み対応 - 設計決定事項

## 概要

N+1問題に対応するため、`RepositoryInterface::fill`メソッドを以下のように拡張する：

1. 第1引数を、エンティティ単体またはエンティティの配列を受け付ける形にする
2. `fill`メソッドは、リレーションとして読み込まれたエンティティ配列を返す形にする
3. **重要**: `fill`実行後、各エンティティのリレーションプロパティにも設定されるため、`$entity->get('relation')`で取得可能

## 設計決定事項

### 1. 戻り値の型と意味

#### 1.1 リレーションタイプごとの戻り値

**決定**: 一貫性のため、すべてのリレーションタイプで配列を返す。`HasOne`や`BelongsTo`の場合も、要素数が0または1の配列として返す。

- **HasMany**: 配列を返す（複数の子エンティティ）
- **HasOne**: 配列を返す（要素数0または1）
- **BelongsTo**: 配列を返す（要素数0または1）
- **BelongsToOne**: 配列を返す（要素数0または1）

```php
// 使用例
$profiles = $userRepo->fill($users, 'profile'); // Profile[]
$user[0]->get('profile'); // Profile|null - エンティティ内のリレーションから取得可能

// 一対多を二度呼び出す場合（主な用途）
$posts = $userRepo->fill($users, 'posts'); // Post[]
$comments = $postRepo->fill($posts, 'comments'); // Comment[]
```

#### 1.2 戻り値の型定義

```php
/**
 * @param EntityInterface|array<EntityInterface> $entities
 * @param string $relationName
 * @return EntityInterface[] リレーションとして読み込まれたエンティティの配列
 */
public function fill(EntityInterface|array $entities, string $relationName): array;
```

**質問**: 戻り値の型をより具体的に指定できるか？（例: `@return T[]` ただしTはリレーション先のエンティティ型）

### 2. 既存コードとの互換性

#### 2.1 戻り値の変更

現在の`fill`は`void`を返すが、配列を返すように変更する。

**影響範囲**:
- `tests/Users/UserRepository.php`: `fillPosts()`, `fillProfile()`
- `tests/Users/PostsRepository.php`: `fillUser()`
- テストコード: `OneToManyTest.php`, `HasOneTest.php`

**対応方針**:
- 既存のコードは動作し続ける（戻り値を使用していないため）
- ただし、戻り値を使用する新しいコードを書けるようになる

#### 2.2 エンティティへの設定動作

**決定**: バッチ読み込み時も、各エンティティのリレーションプロパティに設定する。既存の動作を維持し、戻り値としても返す。

**重要な動作**:
- `fill`実行後、各エンティティのリレーションプロパティに相手のエンティティが設定される
- これにより、`$entity->get('relation')`で取得可能
- 独自Hydratorを使う場合は、自分で設定することも可能

```php
// 既存の使い方（動作し続ける）
$userRepo->fill($user, 'posts');
$posts = $user->get('posts'); // Post[]

// 新しい使い方（チェーン可能）
$posts = $userRepo->fill($users, 'posts'); // Post[]
$user[0]->get('posts'); // Post[] - エンティティ内のリレーションから取得可能
$comments = $postRepo->fill($posts, 'comments'); // Comment[]
```

### 3. バッチ読み込みの実装詳細

#### 3.1 WHERE IN クエリの実装

複数のエンティティに対して、`WHERE foreign_key IN (...)` で一括取得する。

**実装方針**:
1. 第1引数が配列の場合、すべてのエンティティのIDを収集
2. `WHERE foreign_key IN (id1, id2, ...)` で一括取得
3. 取得したエンティティを、親エンティティのIDでマッピング
4. 各親エンティティにリレーションを設定

**注意点**:
- IDが`null`のエンティティはスキップするか？
- 空配列が渡された場合の動作
- 重複IDの処理

#### 3.2 リレーションタイプごとの処理

- **HasMany**: 各親IDに対して、複数の子エンティティをマッピング
- **HasOne**: 各親IDに対して、1つの子エンティティをマッピング（複数見つかった場合は例外？）
- **BelongsTo**: 各子エンティティの`foreign_key`から親IDを取得し、一括取得
- **BelongsToOne**: `BelongsTo`と同じ

**質問**: `BelongsTo`の場合、子エンティティの`foreign_key`が`null`の場合はどうするか？

#### 3.3 双方向リレーションの設定

**決定**: 双方向リンクの設定について、以下の方針とする：

- **HasOne**: 子エンティティ（profile）に親エンティティ（user）を設定するのはOK
- **HasMany**: 子エンティティ（post）に親エンティティ（user）を設定するのはOK
- **BelongsTo**: 子エンティティ（post）に親エンティティ（user）を設定するのはOK（既に実装済み）

**注意**: HasManyの場合、親エンティティに子エンティティを設定するのは混乱を招く可能性があるため、現在の実装（子エンティティに親エンティティを設定）を維持する。

### 4. エッジケースの処理

#### 4.1 空配列やnullの扱い

- リレーションが見つからない場合の戻り値: 空配列 `[]`
- 第1引数が空配列の場合: 空配列を返す
- 第1引数が`null`の場合: 型エラー（PHP 8.0+の型システムで防げる）

#### 4.2 IDがnullのエンティティ

**決定**: IDが`null`のエンティティはスキップする（警告なし）。N+1問題の解決が主目的であり、IDが`null`のエンティティは通常、保存前のエンティティである可能性が高い。

#### 4.3 重複エンティティ

- 同じエンティティが配列に複数回含まれている場合の処理

**提案**: 重複を除去して処理する（`array_unique`的な処理は不要。IDでマッピングするため、自然に重複が解決される）

### 5. パフォーマンス考慮事項

#### 5.1 クエリの最適化

- `IN`句の要素数に制限がある場合（例: MySQLの`max_allowed_packet`）
- 大量のエンティティを一度に処理する場合の分割処理

**決定**: 上限はシステム依存（例: MySQLの`max_allowed_packet`）とし、コーディング側で対応してもらう。フレームワーク側では上限を設けない。

#### 5.2 メモリ使用量

- 大量のエンティティを一度に読み込む場合のメモリ使用量

### 6. API設計の一貫性

#### 6.1 メソッド名

**決定**: `fill`のまま。理由：
- 既存コードとの互換性
- `fill`は「埋める」という意味で直感的
- 英語として自然（`include`よりも`fill`の方が適切）
- 単一エンティティでも配列でも同じメソッドを使える

### 7. テスト戦略

#### 7.1 テストケース

以下のテストケースが必要：

1. 単一エンティティ + HasMany
2. 単一エンティティ + HasOne
3. 単一エンティティ + BelongsTo
4. エンティティ配列 + HasMany（バッチ読み込み）
5. エンティティ配列 + HasOne（バッチ読み込み）
6. エンティティ配列 + BelongsTo（バッチ読み込み）
7. 空配列を渡した場合
8. IDがnullのエンティティを含む場合
9. 重複エンティティを含む場合
10. リレーションが見つからない場合（空配列を返す）

#### 7.2 既存テストの更新

既存のテストは動作し続けるべきだが、戻り値の検証を追加するか？

**提案**: 既存テストはそのまま動作することを確認し、新しいテストケースで戻り値を検証する。

### 8. 実装の段階的アプローチ

#### 8.1 フェーズ1: インターフェースの変更

1. `RepositoryInterface::fill`のシグネチャを変更
2. 既存の実装を更新（単一エンティティの場合のみ対応）
3. 既存テストが動作することを確認

#### 8.2 フェーズ2: バッチ読み込みの実装

1. 配列を受け付ける処理を追加
2. `WHERE IN`クエリの実装
3. マッピング処理の実装
4. 新しいテストケースの追加

#### 8.3 フェーズ3: 最適化とドキュメント

1. パフォーマンステスト
2. ドキュメントの更新
3. 使用例の追加

## 設計決定まとめ

1. **戻り値の型**: ✅ すべて配列で統一（一貫性のため）
2. **エンティティへの設定**: ✅ はい。各エンティティのリレーションプロパティに設定する（既存の動作を維持）
3. **IDがnullのエンティティ**: ✅ スキップ（警告なし）
4. **メソッド名**: ✅ `fill`のまま（既存コードとの互換性、英語として自然）
5. **上限**: ✅ システム依存で、コーディング側で対応
6. **実装順序**: ✅ HasMany → HasOne → BelongsTo（使用頻度の高い順）

## 重要な動作確認

`fill`実行後、エンティティ内のリレーションプロパティにも設定されるため、以下のように使用可能：

```php
$profiles = $userRepo->fill($users, 'profile');
$user[0]->get('profile'); // Profile|null - エンティティ内のリレーションから取得可能
```

これにより、既存のコード（`$entity->get('relation')`）も動作し続け、新しいコードでは戻り値を使ってチェーンできる。
